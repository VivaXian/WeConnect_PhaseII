# 历史设备与数据迁移

面向从原报修平台引流至小程序的存量用户。

相关代码：`src/stores/migration-store.ts`、`src/pages/user-device-page.tsx`、`src/components/role-switcher.tsx`（演示用）

---

## 1. 背景与问题

原报修平台的用户被引导至小程序，我们已告知会迁移其历史数据。但实际迁移**不是注册即时完成**，而是由团队**每周统一推送一次**。

由此产生的问题：用户注册完进入小程序，看到「我的设备」空空如也，会认为"说好的迁移没做"或"这个小程序没数据、没用"。这段落差最长可持续一周。

### 为什么不能只用弹窗

最初的设想是注册后弹一个弹窗告知。但：

- 弹窗是**一次性**的，用户的困惑是**持续一周**的
- 注册完成那一刻用户注意力在"走完流程"上，弹窗大概率被秒关
- 真正产生困惑的时刻是接下来七天里**每次打开设备列表**的时候，那时弹窗早已消失
- 弹窗还挡住了这个页面唯一有用的操作（扫码绑定）

因此方案分两层，**权重在第二层**：一次性弹窗承担"告知契约"，页面常驻状态承担"消解困惑"。

## 2. 状态机

```
none ──────► pending ──────► done
（无迁移）    （迁移中）      （已完成）
```

| 状态 | 含义 |
| --- | --- |
| `none` | 该用户无历史数据可迁移（全新用户），或迁移完成后的提示已消费完毕 |
| `pending` | 已确认有历史数据待迁移，等待下一批次 |
| `done` | 迁移已完成，尚未向用户展示完成提示 |

**状态必须由服务端下发，不能由前端推断。需服务端。**

> 关键：**不要用"设备列表为空"来推断迁移状态**。一个把设备全部解绑的老用户列表也是空的，如果靠列表为空来判断，他会看到"历史设备迁移中"，这是明显的错误信息。

建议接口字段（随用户 profile 返回）：

```jsonc
{
  "migration": {
    "status": "pending",              // none | pending | done
    "expectedAt": "2026-08-17",       // pending 时必填，预计完成日期
    "migratedCount": 13               // done 时必填，本次迁入设备数
  }
}
```

## 3. 各状态的界面

### 3.1 pending + 设备列表为空

空态整体替换为迁移态：

```
┌ 扫设备码 ┐  ┌ 输入编号 ┐
│报修 / 绑定│  │报修 / 绑定│
└─────────┘  └─────────┘

   [DownloadCloud 插画]
  历史设备与数据迁移中
   预计 8月17日前完成
```

- 插画使用 Filament `DownloadCloud`（**不是** `Hourglass`）。沙漏只表达"在等"，下载云表达"东西正在过来"，且自带方向感
- `size="medium"`（96×96）
- 扫码/输入两张操作卡片保留在插画上方：等待期间用户仍可能有急修需求，这是唯一的出口

**这一层最重要。** 它取代了原来的「暂无绑定设备」——后者在此场景下是**错误信息**，它告诉用户"你没有设备"，而事实是"你的设备在路上"。

**已实现。**

### 3.2 pending + 设备列表非空

用户在等待期间自己绑定了设备后，列表不再为空，空态消失。此时必须有常驻提示，否则用户会以为"迁移已经完成了，而且只迁过来这一台"。

在列表顶部、「共 N 台设备」上方展示状态条：

```
☁ 历史设备与数据迁移中，预计 8月17日前完成
```

- 蓝色底（`#eaf3ff`），圆角 10，12.5px
- 左侧 `DownloadCloud` 图标 15×15
- **不可关闭**：它是持续状态，关掉等于把用户重新扔回困惑里；迁移完成后自动消失

**已实现。**

> 3.1 与 3.2 互斥，不会同时出现。

### 3.3 done — 首次查看

弹窗（一次性）：

> **历史设备与数据迁移完成**
>
> 已为你迁入 13 台设备及其历史报修记录。
>
> `[ 知道了 ]`

页面状态条（绿色底 `#e8f6ee`，与迁移中的蓝色条同尺寸、同圆角、同字号）：

```
✓ 已迁入 13 台历史设备及报修记录            ✕
```

- **可关闭**：这是已完成的事件，不是持续状态。用户确认过就该让位给列表
- 关闭状态需持久化，不要下次进入又出现

**已实现。**

> 迁移中的条不可关闭、迁移完成的条可关闭 —— 这个差异是有意的，不要统一。

### 3.4 完成后是否发服务通知

**不发。** 迁移完成不推送服务通知，用户下次打开小程序时通过弹窗 + 状态条得知。

（早期文案中有"迁移完成后会发送服务通知"，已删除。做不到的承诺不能写。）

## 4. 数据合并规则（核心）

> 这一节是本文档最需要开发确认的部分。

迁移不是简单的"插入新记录"，因为**同一台设备可能在两边都有数据**：用户在等待迁移期间，很可能已经在小程序里自己绑定了某台设备、甚至提交了报修。当这台设备的历史数据从旧平台迁过来时，必须合并而不是产生两条。

### 4.1 设备去重

**判定规则（已确认）：**

两侧的设备唯一标识完全一致，以此作为合并主键：

- `serialNumber`（序列号）
- `eqNumber`（EQ 号）

两者任一完全匹配即判定为同一台设备。**不允许使用模糊匹配、不允许用 `deviceName + hospital` 匹配**（原因见 4.3）。

开发注意：匹配前建议做基础归一化（去首尾空格、统一大小写、去除全角字符），以防旧平台录入时的格式差异导致同一台设备未能命中。归一化后仍不一致的视为不同设备。

**合并规则：**

| 情况 | 处理 |
| --- | --- |
| 旧平台有、小程序无 | 新增设备，绑定给该用户 |
| 旧平台有、小程序也有（用户已自行绑定） | **合并为一条**，不新增；保留小程序侧的设备记录为主体，将旧平台数据挂载上去 |
| 旧平台无、小程序有 | 保持不变 |

**合并后必须保证：**

- 「我的设备」列表中该设备**只出现一次**
- 用户自行设置的**设备备注不被覆盖**（备注是用户自己写的，迁移数据不应覆盖用户输入）
- `migratedCount` 计数应为**实际新增**的设备数，不包含被合并掉的重复项 —— 否则弹窗说"已迁入 13 台"但列表只多了 8 台，用户会困惑

**需服务端。**

### 4.2 报修记录合并

同一台设备在旧平台的报修记录与在小程序的报修记录，**必须合并到同一台设备下**，按时间倒序统一排列，而不是分成两个列表或两个入口。

用户视角里这就是"这台机器的报修历史"，不该因为系统迁移而被切成两段。

**建议保留来源标记**用于排查问题，但**默认不在界面上区分展示**。原型的 `RepairRecord` 类型中已有相关字段可复用：

```ts
source?: 'mini-program' | 'phone' | 'service-account'
```

**需服务端。**

#### 分界线是日期，不是手写标记（已实现）

**2026-04-18 是小程序上线日。** 在这之前不存在"小程序报修"这回事 —— 所有报修都是电话或服务号进来的，也就都没有图文沟通记录、没有逐条维修进度、没有可下载的工单详情。

判据只有一条，从 `repairTime` 推导，不要再维护布尔标记：

```ts
// utils/repair-cutoff.ts
export const REPAIR_SYNC_CUTOFF = '2026-04-18';
export const isPreCutoffRepair = (record) => record.repairTime < REPAIR_SYNC_CUTOFF;
```

原来的 `legacyProgress?: boolean` 已删除。手写标记和日期会各说各话 —— 曾经有 5 条标了 `legacyProgress`、另外 4 条同样早于 4/18 却没标，于是同一时期的报修在详情页长得不一样。一个真相来源，新增数据不会漏标。

由此产生两条数据约束：**未结束的 case（`reported` / `in-service`）必须在 4/18 之后** —— 一个 2 月报的单子今天还挂着「服务中」，却顶着「进度无法追溯」的说明，是自相矛盾的；**4/18 之前不得出现 `source: 'mini-program'`**。

#### 4/18 之前的报修：三个结构性差异（已实现）

`isPreCutoffRepair(record)` 为真的记录，详情页与小程序原生报修不同，**不要把缺失的部分假装成正常态**：

| 区块 | 小程序原生报修 | 4/18 之前的报修 |
| --- | --- | --- |
| 服务对话 | 有入口 | **不展示**。当时根本不存在图文沟通，给一个空入口只会让用户白点 |
| 工单信息 | 可点入工单详情、可签字 | 只展示工单号（静态行，不可点）。**工单号是有的，缺的只是工单详情** |
| 维修进度 | 步骤条 + 时间轴 | 只展示步骤条。最终状态是已知事实，缺的只是逐条时间轴 |

#### 缺失说明只出现一次，放在页面顶部

上面三处缺失是**同一个原因**造成的。不要在每个小节里各放一条说明 —— 曾经在「工单信息」和「维修进度」各挂一条，同一件事说两遍，页面看上去像出了两个故障。

正确做法：**一条**说明，**写在副头（报修编号 / 状态 / tagline）的白底区块内部**，靠一条发丝线（`rdStyles.noticeBar`）与上文隔开，各小节只是安静地少展示内容，不再自我解释。

> 由于系统升级，2026年4月18日前的报修记录无法完整同步。如需工单详情，**请联系客户响应中心**。

三个节拍：原因 → 事实（记录不完整）→ 出口。

**要点：**

- **日期必须写出来。** 它同时告诉用户「4月18日之后的报修这些都有」，把缺失框定成一次性的历史问题，而不是产品常态。删掉日期看似更"通用"，实际是把可判断的规则退化成模糊的抱歉。
- **不要逐项点名缺了什么。** 曾经写过「维修进度明细无法追溯」—— 用户往下一看，缺什么自己就看到了（只有步骤条、工单不可点），文案再拆一遍只是把一句话拉长。一句总述 + 一个出口就够。
- **用页面自己的词。** 「工单详情」是页面上真实缺失的东西（工单号在、详情不在），用户才能把这句话对到屏幕上少的那块东西。
- **`cancelled` 的报修不显示这条。** 取消的报修没有维修过程可追溯、也没有工单，「如需工单详情」是张空头支票。
- **不要做成卡片。** 试过琥珀色警示条和灰底圆角框，两者都错：琥珀把背景说明抬成告警；灰底框浮在浅蓝页面底上，上下各多出一道蓝缝，分量反而比正文还重。现在是白底上的 12px 灰字 + 内联蓝链，跟副头同处一块白区。

文案约束：

| 不要写 | 原因 |
| --- | --- |
| 「旧平台」 | 用户不需要知道内部有几个系统，也不该被强化这个概念 |
| 「纸质签字」 | 过去也可能是电子签单，只是没走小程序 —— 断言签字形式会说错 |
| 「小程序上线」 | 对用户来说这只是一次系统升级，不必解释内部里程碑 |
| 「未同步到小程序」 | 暗示背后有两个系统在对账，那是内部管道 |
| 「仅保留工单号」 | 过度承诺。工单号在「工单信息」里明摆着，不需要文案再声明一遍 |
| 「电话报修」 | 缺失由时间点决定、与渠道无关；写渠道会漏掉服务号、线下等情况 |

#### 「请联系客户响应中心」必须直达，并把话替用户起个头

链接**不能**走 `ensureRepairConversation`。那条路是死的，曾经的完整链条：

1. 凭空创建一条报修维度对话，还伪造一句客户响应中心问候语（对 4/18 前的 case 而言，正好违背"不该有对话"）；
2. `isConversationClosed` 判定 `completed-pending` / `cancelled` 的 case 对话一律关闭 → 输入框被换成「再次咨询」按钮；
3. 「再次咨询」把 `caseRef` 传给 `startGeneralInquiry`，而那个函数的参数写成 `_relatedCaseRef`，**根本没用**；
4. 落到空的通用对话，让用户自己开 `QuickEntryCard` 选报修 —— 而选择器用的是 `activeRepairs()`，只列 `reported | in-service`，**已完成的 case 压根不在列表里**。

正确做法：`startGeneralInquiry(caseRef)` 跳到 `GENERAL_CONVERSATION_ID`，`caseRef` 随导航状态（`NavState.attachedCase`）传进 `ConversationPage`，在那里换算成一句**预填在输入框里的草稿**交给 `MessageComposer initialDraft`：

> 我要咨询报修单 D-12126598

**预填草稿，不是挂标签。** 试过在输入框上方挂一个「关联报修 设备名 · 报修号 ×」的 chip，问题是**它看着不像"已经关联上了"**，更像一个装饰性标记；用户还得自己猜发送时会发生什么。预填一句人话，用户一眼就知道这条消息将要说什么，也可以直接改写、补充，然后照常发送 —— 之后就是等客户响应中心回复，没有任何额外机制。

**不要自动发送。** 预填是替用户起个头，替他按下发送就是替他发言 —— 他真正想问什么，我们并不知道。

**预填时不要再走 `relatedCase`。** 那个 prop 会在发送时给正文加 `【设备名 · 报修号】` 前缀，和草稿里的报修单号重复。通用对话传 `undefined`，报修维度对话才传 `caseRef`。

**case 已带过来时，通用对话开场的 `QuickEntryCard` 不出现**（`ConversationThread onQuickEntry` 传 `undefined`），否则等于话都替他写好了又问一遍"您想咨询什么"。输入框上方的「选择设备或报修单」按钮保留，用户可以改。

#### 兜底入口：4/18 之后的服务完成报修

「需要进一步信息？联系客户响应中心」用于 `status === 'completed-pending' && !isPreCutoff` —— 服务完成之后工程师沟通渠道已经关闭，用户再有问题只剩这一个出口。

4/18 之前的报修**不显示这一行**，因为顶部说明里已经带了同一个链接。一个页面永远只有一个客户响应中心出口。

位置在**维修进度小节之后、报修描述之前**，不要压在页面最底部：用户看完进度产生疑问就在这里，翻到最后才看到已经晚了。样式是一行居中小字（`rdStyles.quietInquiry`），不是卡片。

**数据里必须始终留一条 4/18 之后的服务完成报修。** 否则这一行永远跑不到，也没有"正常已完成报修"的样例可看（完整时间轴 + 可点工单 + 服务对话入口）。当前的样例是 `jul26-1`（D-12126628 · Azurion M3 · 2026-07），它同时是唯一一条示范 `source: 'mini-program'` 已结单的记录，并配了一条 closed 的服务对话种子、一张真实存在的工单（`wo-016`，`work-order-data.ts` 里有对应条目，不是死链）。

挑设备时注意：**不要把"服务完成"挂到一台 `status: 'pending-repair'` 的设备上**。Elition 磁共振有一条 4 月的在途报修（`apr26-1`，四种工单状态的样例），再给它加一条 7 月已完成的报修，就成了"设备从 4 月修到现在，中间还完整修好过一次"。Azurion M3 是 `status: 'normal'` 且没有在途 case，才是合适的宿主。

相应地，**对话种子数据不得挂在 4/18 之前的 case 上**。

#### 迁移进行中的旧报修单 — 待确认

报修单的进展提醒是绑定在 Case 上的订阅（见 [device-unbind.md](device-unbind.md#43-服务提醒与消息推送)）。但从旧平台迁过来的**未关闭**报修单，用户当初的订阅建立在旧平台，不是微信订阅消息。

因此需明确：迁移过来的在途报修单，其后续进展是否推送给用户？如果推，订阅关系由谁、在什么时机建立？（迁移时自动建立订阅在微信侧通常不被允许，可能需要用户在小程序内查看该单时补充授权。）

**待确认。**

### 4.3 当前数据结构的隐患（重要）

原型中 `RepairRecord` **没有 `deviceId` 字段**，报修记录与设备的关联是靠**设备名称匹配**的：

```ts
// src/pages/super-user-service-page.tsx
const device = deviceList.find((d) => d.name === deviceName);
```

这个关联方式在迁移场景下会出问题：

- 旧平台与小程序对同一台设备的命名很可能不一致（`EPIQ 5` vs `EPIQ5 超声`）
- 用户可以给设备加备注/改显示名
- 同一院区可能有多台同型号设备，名称完全相同

**要求：报修记录、工单记录必须以稳定的设备主键（`deviceId`）关联，不能依赖名称匹配。** 设备侧已确认用 EQ 号 / 序列号做合并主键（4.1），但报修记录目前连设备主键都没有 —— 即使设备合并对了，报修记录也挂不上去。迁移方案设计时必须先解决这个关联问题。

**需服务端 + 待实现。**

### 4.4 迁移与解绑的交叉情况

用户在 `pending` 期间自行绑定了设备 A，随后又把 A 解绑了。此时迁移批次到达，其中包含设备 A。

**建议规则（待确认）：** 尊重用户的显式操作，A 不重新出现在「我的设备」中，但其历史数据正常合并（用户重新绑定 A 时应能看到完整历史）。

理由：解绑是用户主动做出的决定，系统的批量操作不应覆盖用户的显式意图。

**待确认。**

## 5. 时间与批次

- 迁移按**每周一批次**执行（原型中 `BATCH_WEEKDAY = 1`，即周一）
- `expectedAt` 应为**服务端按用户注册时间算出的下一个批次日期**，随 profile 下发
- 前端只负责格式化展示（`M月D日`）

### 为什么必须给具体日期

不要写"一周内"或"请耐心等待"。给出"8月17日"用户可以自己判断还剩几天，焦虑远低于模糊表述；写"一周内"则用户每天都要重新猜一遍。

**已实现**（原型中前端计算，生产环境改为服务端下发）。

### 6.2 写作要点

**用"会自动迁移过来"，不用"正在迁移中"作为正文动词。** 后者暗示有个进度条在跑，用户会追问"为什么这么慢"；前者是承诺，不是进度。

**不要出现"分批""每周统一推送"等内部流程词。** 用户不需要理解排期机制，只需要知道 what + when。说了反而显得"我们没能力实时处理"。

**迁移中弹窗的第二句是最有价值的一句** —— 给出口。没有它，这个弹窗只是一条坏消息。

**迁移中弹窗允许分两段**（承诺 / 出口是两件独立的事），但完成弹窗只用一句。参见 [device-unbind.md](device-unbind.md#62-写作要点) 中关于折行的判断标准。

## 7. 触发与展示次数

| 提示 | 触发条件 | 展示次数 |
| --- | --- | --- |
| 迁移中弹窗 | `status === 'pending'` 且未读 | 每个账号一次 |
| 迁移中空态 / 状态条 | `status === 'pending'` | 持续显示至状态变更 |
| 完成弹窗 | `status === 'done'` 且未读 | 每个账号一次 |
| 完成状态条 | `status === 'done'` 且未手动关闭 | 直至用户关闭 |

**弹窗时机：不要挂在注册流程的最后一步，要挂在用户第一次进入「我的设备」Tab 时。** 注册完成页上用户正在连续点"下一步/完成"，紧跟着的弹窗会被当成流程的一部分无脑关掉。

"已读"标记原型中存于 localStorage，**生产环境应存于服务端并按用户 ID 隔离**，否则用户换设备登录会重复看到。**需服务端。**

## 8. 前端实现现状

原型状态（`src/stores/migration-store.ts`）：

```ts
status: 'none' | 'pending' | 'done'
expectedAt: string          // ISO 日期
noticeSeen: boolean         // 迁移中弹窗已读
migratedCount: number
doneNoticeSeen: boolean     // 完成弹窗已读
doneBannerDismissed: boolean
```

接入真实接口时，`status` / `expectedAt` / `migratedCount` 改为服务端下发，三个已读标记改为服务端存储，其余 UI 逻辑不需改动。

### 演示方式

角色切换器（`src/components/role-switcher.tsx`）提供四个演示模式，仅用于原型演示，生产代码中应移除：

| 模式 | 效果 |
| --- | --- |
| 新用户 | 清空全部绑定 → `pending` → 触发迁移中弹窗与空态 |
| 迁移完成 | 恢复全部设备 → `done` → 触发完成弹窗与绿色状态条 |
| 认证用户 | 普通认证用户，无迁移态 |
| 授权用户 | 院方管理员视角 |
