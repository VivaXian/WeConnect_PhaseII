# 设备解绑

适用角色：认证用户（`role === 'user'`）。授权用户（院方管理员）不提供解绑能力。

相关代码：`src/pages/user-device-page.tsx`、`src/pages/device-detail-info-tab.tsx`、`src/components/recently-unbound-sheet.tsx`、`src/stores/device-binding-store.ts`

---

## 1. 设计原则

**解绑是「从我的设备列表移除」，不是「删除设备」。**

这条原则决定了后面所有的数据规则。用户解绑的动机通常是"这台机器不归我管了"或"列表太长想清理"，而不是"我要删掉这台设备的所有痕迹"。因此：

- 设备主数据、报修记录、工单记录一律保留
- 解绑可逆，且提供两条回头路（30 天内一键恢复 / 任何时候重新绑定）
- 解绑不需要二次校验（不是危险操作），但需要明确的确认弹窗说明影响范围

## 2. 交互流程

### 2.1 批量解绑（列表内就地管理）

入口在「我的设备」列表头部，与「共 N 台设备」同一行：

```
共 12 台设备 │ 管理                    排序 ▾
```

- 「管理」为纯文字按钮，无图标，蓝色 13px
- 设备数为 0 时不显示「管理」
- 点击后列表**就地**进入选择态，不跳转新页面

进入管理模式后：

| 区域 | 变化 |
| --- | --- |
| 列表头部右侧 | 排序控件 → 「最近解绑 N ›」入口（N 为 0 时不显示） |
| 设备卡片 | 左侧出现选择圆点，点击整卡切换选中，不再跳转详情 |
| 页面底部 | 出现操作条，固定在 Tab 栏上方 |

底部操作条：

```
全选 / 取消全选    已选 N 台          [取消]  [解绑设备]
```

- 「解绑设备」为 `variant="primary" signal="danger"`，未选中任何设备时禁用
- 「取消」退出管理模式并清空选择

**已实现。**

### 2.2 单台解绑

设备详情页 → 信息 Tab → 「解绑设备」。使用同一套确认弹窗文案。**已实现。**

### 2.3 确认弹窗

标题（批量）：`解绑所选 N 台设备？`
标题（单台）：`解绑「设备名」？`

正文（两处共用，单段不换行）：

> 仅从「我的设备」移除，设备相关数据仍保留在飞利浦服务器，可再次绑定或30天内通过「最近解绑」恢复

按钮：`取消` / `解绑设备`（危险态）

**已实现。**

> 文案注意事项见第 6 节。**正文必须是单段连续文本，不要插入手动换行符**。

### 2.4 解绑后反馈

Toast：`已解绑 N 台设备`，附两个操作：

| 操作 | 行为 |
| --- | --- |
| 查看 | 打开「最近解绑」半屏面板 |
| 撤销 | 恢复本次解绑的全部设备 |

Toast 停留 4 秒。**已实现。**

## 3. 最近解绑

30 天恢复期的入口，以**半屏面板**呈现，不是独立页面、不是 Tab。

### 3.1 入口

| 场景 | 入口位置 |
| --- | --- |
| 管理模式中 | 列表头部右侧「最近解绑 N ›」 |
| 设备数为 0 的空态 | 空态底部「查看最近解绑 N ›」 |
| 解绑后 Toast | 「查看」按钮 |

N 为 0 时所有入口都不显示。

### 3.2 面板内容

顶部说明：`解绑的设备保留 30 天，到期后自动移除。`

每行结构：

```
设备名（备注）
医院名称                        ← 仅当用户名下有多个院区时显示
超声 · 超声科 门诊楼2层
EQ 2093735 · SN US-2021-0764
28 天后自动移除                 ← 橙色
                        [恢复]
```

**已实现。**

### 3.3 院区显示规则（重要）

**最近解绑列表不跟随「我的设备」的院区筛选。** 无论当前筛选的是哪个院区，面板中始终展示全部已解绑设备。

理由：最近解绑是**兜底/找回**界面，用户来这里是因为"少了一台设备"。如果它跟着筛选走，用户在 A 院区筛选下找不到自己刚在 B 院区解绑的设备，会误判为"数据丢了"。找回类界面必须给全集。

配套规则：

- 用户名下有多个院区 → 每行显示医院名称，独立成行
- 用户名下只有一个院区 → 省略医院名称（无信息量）

**已实现**（`showCampus={hasMultipleCampuses}`）。

医院名称的截断规则见 [common-display-rules.md](common-display-rules.md)。

### 3.4 恢复

点击「恢复」立即生效，设备回到「我的设备」，从最近解绑列表移除。Toast：`已恢复「设备名」`。

**已实现。**

### 3.5 过期清理

超过 30 天的记录从最近解绑列表消失，设备进入"已解绑且不可一键恢复"状态。用户仍可通过扫码或输入编号重新绑定。

- 原型实现：前端按 `removedAt` 时间戳判断（`isWithinRetention`），未做真正的清理任务
- 生产实现：**需服务端**。清理由服务端定时任务执行，前端不应依赖客户端时间判断过期

## 4. 数据规则（核心）

> 这一节是本文档最需要开发确认的部分。

### 4.1 解绑影响范围

| 数据 | 解绑后 | 状态 |
| --- | --- | --- |
| 我的设备列表 | 移除 | 已实现 |
| 个人中心「关联 N 台设备」 | N 减少，院区数同步重算 | 已实现 |
| 报修列表（我的报修） | **不受影响，记录保留** | 已实现（未做过滤） |
| 工单列表 | **不受影响，记录保留** | 已实现（未做过滤） |
| 设备主数据 | 不删除 | 需服务端 |
| 历史报修记录 | 不删除 | 需服务端 |
| 保养计划 | 不删除 | 需服务端 |

**报修列表与工单列表不做绑定态过滤，是有意为之，不是遗漏。**

理由：用户解绑设备时，手上可能还有该设备**未完成的报修单**。如果解绑连带把报修记录从列表里抹掉，用户会以为报修被取消了，这是严重的信任事故。报修单的生命周期由报修流程决定，与设备绑定关系无关。

> 开发注意：原型中报修列表恰好没有做绑定态过滤，行为符合预期，但这是"从未写过过滤逻辑"的结果，不是显式规则。生产实现中请**显式**确保不加这层过滤，并在代码或接口文档中注明原因，避免后续被当成 bug"修掉"。

### 4.2 个人中心设备数

个人中心展示 `关联 N 台设备 | 覆盖 M 个院区`。

- N = 已绑定设备数（排除已解绑、已过期清理的）
- M = 上述设备去重后的院区数

必须与「我的设备」列表的「共 N 台设备」一致。解绑后两处同时变化。

**已实现**（`src/pages/profile-page.tsx` 的 `deviceSummaryLabel`，与列表消费同一份绑定状态）。

> 开发注意：生产实现中这两个数字应来自**同一个接口字段或同一份计算逻辑**，不要各算各的。原型中它们共享同一个 store，天然一致；如果生产环境改成两个接口分别返回，很容易出现不一致。

### 4.3 服务提醒与消息推送

判断依据是**订阅挂在什么对象上**，而不是"解绑了就全停"：

| 消息类型 | 订阅对象 | 解绑后 |
| --- | --- | --- |
| 设备保养提醒 | 设备 | **停止推送** |
| 合同到期提醒 | 设备 | **停止推送** |
| 报修单进展通知 | 报修 Case | **继续推送**，不受解绑影响 |
| 工单进展通知 | 工单 | **继续推送**，不受解绑影响 |

设备类提醒的前提是"我管这台设备"，解绑即意味着这个前提不成立了。而报修单的订阅是用户提交该 Case 时建立的，与设备绑定关系无关 —— 解绑不应中断一个进行中的服务承诺。

> 这条规则与 4.1 的"报修/工单列表不做绑定态过滤"是同一逻辑的两面：**设备维度的东西跟着绑定关系走，Case 维度的东西跟着 Case 自己的生命周期走。**

原型中消息列表未做任何绑定态过滤。生产实现需按上表区分：**设备维度的消息需要在解绑时退订，Case 维度的消息不动。待实现。**

### 4.4 重新绑定

用户可通过扫码或输入设备编号重新绑定已解绑的设备。重新绑定后：

- 设备回到「我的设备」
- 该设备的历史报修记录、工单记录应完整可见（不因中间解绑过而丢失）

**需服务端。**

## 5. 空态

设备数为 0 时的空态，操作优先于说明：

```
┌ 扫设备码 ┐  ┌ 输入编号 ┐
│报修 / 绑定│  │报修 / 绑定│
└─────────┘  └─────────┘

     [FolderEmpty 插画]
       暂无绑定设备
   查看最近解绑 (12) ›
```

- 两张操作卡片在插画**上方**：这个页面用户唯一要做的事就是绑设备，插画和文字只解释"为什么这里是空的"，属于次要信息
- 「查看最近解绑」仅当有可恢复设备时显示
- 插画使用 Filament `FolderEmpty`，`size="medium"`（96×96）。`large`（144×144）在 375px 宽度下过于抢眼

筛选后无结果的空态使用 `NoResult` 插画 + `无匹配设备` + 「清除筛选条件」按钮。

**已实现。**

## 6. 文案规范

### 6.1 定稿文案

| 位置 | 文案 |
| --- | --- |
| 列表头部入口 | `管理` |
| 底部操作条主按钮 | `解绑设备` |
| 确认弹窗标题（批量） | `解绑所选 N 台设备？` |
| 确认弹窗标题（单台） | `解绑「设备名」？` |
| 确认弹窗正文 | `仅从「我的设备」移除，设备相关数据仍保留在飞利浦服务器，可再次绑定或30天内通过「最近解绑」恢复` |
| 确认弹窗按钮 | `取消` / `解绑设备` |
| 解绑成功 Toast | `已解绑 N 台设备`，操作 `查看` `撤销` |
| 恢复成功 Toast | `已恢复「设备名」` |
| 面板标题 | `最近解绑` |
| 面板说明 | `解绑的设备保留 30 天，到期后自动移除。` |
| 面板倒计时 | `N 天后自动移除` |
| 面板空态 | `暂无最近解绑的设备` |
| 列表空态标题 | `暂无绑定设备` |
| 筛选空态标题 | `无匹配设备` |

### 6.2 写作要点

**「仅」字不能删。** 它界定影响范围。没有它，"从「我的设备」移除"是开放式表述，用户不知道还会连带发生什么。这一个字替代了原来整句"不再收到服务提醒"。

> 保养提醒确实会停（见 4.3），但不在弹窗里写。它是"移除设备"的必然结果而非独立后果，单列一句会让用户以为解绑还有别的隐藏影响，反而制造不安。真正需要担心的"报修单还跟不跟我"，答案是跟 —— 不需要提醒用户去担心一件不会发生的事。

**恢复路径按成本排序。** 先说 30 天内一键恢复，再说重新绑定。反过来写会让用户以为只能重新绑。

**弹窗正文不要手动换行。** 375px 宽度下，两段文字会各自折行变成 4 行，且强制断点落在句子中间，读起来是碎片而非一段话。让文本自然折行。

判断标准：**分段的收益要能盖过折行的代价**。两个真正独立的动作（如"承诺 + 出口"）值得分段；一句因果连贯的解释不要硬拆。

**不要出现内部流程词。** 用户不需要理解回收机制、清理任务的实现方式。

绑定状态数据结构（原型）：

```ts
removedIds: string[]                  // 已解绑、仍在 30 天恢复期内
removedAt: Record<string, string>     // 解绑时间戳，用于倒计时
purgedIds: string[]                   // 已彻底移除（过期或手动清理）
RECYCLE_RETENTION_DAYS = 30
```

生产实现中，设备的绑定状态应由服务端返回，前端不维护 `removedIds` 这类本地集合。倒计时天数建议由服务端直接下发，避免客户端时区/时间不准导致显示偏差。
