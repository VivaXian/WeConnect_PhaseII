# 用户主动问询 — 本版降级方案

> 状态：本版**不上线**用户主动发起的图文咨询。
> 本文记录被移除的内容存放在哪里、原来长什么样、为什么移除、以及将来怎么恢复。

## 1. 背景

后台（客户响应中心 / 远程服务工程师）目前无法保证及时接待用户主动发起的图文问询。
上线一个"可以发，但没人回"的入口，比不上线更伤信任。

因此本版把**对话的所有权从用户移交给工程师**：

| | 原设计 | 本版降级 |
| --- | --- | --- |
| 谁发起 | 用户随时可发起咨询 | 只有远程服务工程师在工单期间发起 |
| 生命周期 | 用户想聊就聊 | 跟随远程服务工单：工单开→可对话，工单关→对话冻结 |
| 产品定位 | 在线咨询 | 服务支持（FAQ + 工程师对话记录） |

一句话：**工程师在工单期间来找你，工单结束，对话也结束。**

## 2. 核心规则

1. **会话开关由远程服务工单控制**，不由报修单状态控制。
   判定见 `src/utils/conversation-status.ts`：
   ```ts
   export const isConversationClosed = (conversation: Conversation): boolean =>
     !conversation.segments.some((segment) => segment.status === 'open');
   ```
   一张远程工单可以在报修单仍是 `in-service` 时就关闭，粒度比报修状态更细。
2. **没有 open segment ⇒ 没有输入框，但要给下一步。**
   输入框原位换成 `ConversationClosedNote`，文案由**报修状态**决定（见第 7 节）。
   这不违背「不补等价 CTA」：给的不是另一个对话入口，而是告诉用户这件事接下来在哪里办。3. **删掉入口 ≠ 必须补等价出口。** 绝大多数被删的入口只是"顺手问一句"的可选便利，不是死路。
   只有真正的死路才补出口，本版只剩 2 处（见第 4 节）。
4. **热线不鼓励拨打**，因此不把热线当作被删入口的通用替代品。
   唯一号码：`400-810-0038`（`SERVICE_HOTLINE`，导出自 `src/components/contact-options-sheet.tsx`）。
5. 底部第三个 tab 由「在线服务」更名为「**服务支持**」。
6. **客户响应中心不再是对话角色。** 用户不能主动发起对话，也就没有「先接入 CCC 再转工程师」这一环。
   CCC 作为**后台职能**依然存在（受理报修、派工、接热线），只是不在小程序里发言。
   因此每段对话的第一条消息就是**工程师本人**的自我介绍，前面配 `HandoffDivider`「远程服务工程师 X 已接入」，
   不再有「已为您安排工程师跟进」这类无作者的调度播报。
7. **工单关闭由工程师侧后台控制，小程序无法干预。**
   所以「关单前必须给结论」只能作为 mock 里的理想样例，**不能当成系统保证**——
   现实中确实可能出现工程师沟通到一半关单、用户以为还能继续说话的情况。
   本版对这个残余风险的唯一交代是 `faq-data.ts` 的 faq-8（见第 5 节），不加任何界面提示。
8. **对话入口统一叫「服务支持」，与底部 tab 同名、同图标（`PersonHeadset`）、同红色数字 `Badge`。**
   不再出现「服务对话」「沟通中」「图文沟通」等平行叫法。三处用同一套词 + 图标 + 角标，
   是为了让用户不需要任何解释就认出「这跟底部那个是同一件事」。共用文案在 `src/utils/service-support-copy.ts`。
9. **工程师名字旁不放沟通按钮。** 圆形沟通图标紧贴姓名，读起来像「点一下就能找他」，
   与「工程师来找你」的方向相反。改为模块底部一整行「服务支持」入口，**电话按钮保留**
   （电话直接打给人，与没人盯的异步信箱是两回事，关单后也不失效）。
10. **入口只在对话真实存在时渲染。** 不得用 `repairConversationId(caseId, CURRENT_USER_ID)` 拼一个
    可能不存在的会话 ID 去跳转——`ensureRepairConversation` 删除后那样做就是死链。
    所有入口改为传真实的 `conversation.id`，`onConversationPress` 统一为 `(conversationId: string) => void`。

设备详情「总览」的那条 strip 是**设备状态告警列表**——待验收 / 报修中 / 即将出保 / 无保 /
保养风险 / 本月保养，每条都是「设备处于 X 状态」+ 一句完整陈述。
把「沟通记录」作为独立一条塞进去有三个问题：(1) 它是**功能入口不是设备状态**，
蓝色 pill 里写「沟通记录」会被读成"设备状态：沟通记录"；(2) 描述「与周工的沟通」是入口副标题语气，
与其余条目的陈述句不同构；(3) 它排在「报修中」上面，但**没有报修就没有对话**，
两条并列把因果拍平了，而且两条蓝色 active 条视觉等重、重要性并不等。

所以合并进「报修中」，落点按是否有进行中的对话分流：

| 情况 | 描述 | 点击落点 |
| --- | --- | --- |
| 有对话 + 有未读 | 服务工程师周工发来 1 条新消息 | 对话 |
| 有对话 + 无未读 | 服务工程师周工正在跟进 | 对话 |
| 无进行中对话 | 设备当前有进行中的报修，工程师处理中 | 报修 tab |

三档都读得通、都是「报修中」这个状态的细化，strip 也回到了纯状态列表。

`本次咨询已结束` 仅保留给 `kind === 'inquiry'` 的历史分段。本版已无 inquiry 分段，该分支与
`conversation-thread.tsx` 的 `SegmentHeader`「飞利浦客户响应中心」一并成为**不可达代码**，保留作恢复路径。
上表三处「远程服务工程师」兜底同理——CCC 不再发言后，`lastResponderMessage` 永远返回 RSE 消息。

`faq-data.ts` 的 **faq-8**「服务已经结束了，还能继续提问吗？」是本版对「工程师关单后用户还想说话」
这一残余风险的唯一交代：

> 已结束的对话会保留供您查阅，但不再接收新消息。如果同一台设备再次出现问题，请重新提交报修，工程师接手后会在新的对话中与您联系。

## 6. 服务支持 tab 的布局与空态

顺序：**常见问题 → 报修对话 → 服务热线**。FAQ 置顶是因为本版用户不能主动发起对话，
自助才是这个页面的主职能；报修对话是工程师来找你的地方，只在有事时才需要注意。

报修对话列表**只展示报修进行中的对话**，报修已结束的折叠到「查看历史记录」里。
一条进行中的都没有时，不能只留一个标题加一个居中链接（看着像加载失败），
而是渲染一行真实内容：「暂无进行中的对话，查看历史记录 ›」。
（「空态不写解释性文案」那条针对的是“一条对话都没有”，与“有历史但没有进行中”是两个状态。）

两种情况下的入口**叫同一个名字、不带任何计数**：有进行中的 → 「查看历史记录 ›」，
没有进行中的 → 「暂无进行中的对话，查看历史记录 ›」。
早期写作「全部报修对话（3）」/「查看历史记录（1）」，两个名字指向同一个页面却叫法不同，
而且两个数字统计口径不一致（一个是总数、一个是归档数），用户无法分辨。

**分组与置灰的依据是报修状态，不是对话是否关闭。** 两者不是一回事：
D-12126572 的远程工单已关（不能再回复），但报修还是服务中。早期版本按 `isConversationClosed`
分组，导致这条被归入「已结束」且头像变灰、状态标消失——屏上写着服务中却是灰的，自相矛盾。
现在统一走 `isCaseClosed(conversation)`（`conversation-status.ts`，内部用 `isRepairStatusClosed`）：

| | 依据 | 用在哪 |
| --- | --- | --- |
| `isCaseClosed` | 报修状态 completed-pending / cancelled | 列表分组、行置灰、状态标 |
| `isConversationClosed` | 没有 open segment | 能不能回复、底部终态 |
| `segment.status === 'closed'` | 单个分段 | 线程内头像置灰 |

行上的状态标直接用 `record.statusTitle`（服务中），不再自己编「等待重新安排」——那是个产品无法保证的承诺。

**完全没有对话时不渲染任何解释性文案。** `ConversationListSection` 直接 `return null`。

### 对话行的标题层级

主标题是**设备名**，次标题是 `报修日期 · 报修号`：

```
[头像] EPIQ Elite                        ❶
       [服务中]  5月21日报修 · D-12126615
       明天上午 9 点后可以进机房，麻烦提前半…  05/22
```

早期版本主标题写「报修号：D-12126615」，设备名降到次标题。这是反的——
**用户不会记得 D-12126615，但一定记得是哪台机器、什么时候报的**；报修号只在需要跟飞利浦核对时才有用，
是次要标识。改动落在 `conversation-display.ts` 的 `conversationTitle` / `conversationMeta` 两个函数上，
所以服务支持首屏、全部报修对话历史页、报修下的多对话列表三处一起生效，不会各写各的。

### 演示数据按角色分化

`Conversation.audience?: 'user' | 'admin'`（演示专用，缺省对所有角色可见），
统一在 `src/hooks/use-visible-conversations.ts` 过滤。**所有读取会话的地方都走这个 hook**，
不要再直接读 `useConversationStore((s) => s.conversations)`，否则角色间会出现不一致
（比如 tab 角标显示未读但列表里没有那条对话）。

| 角色 | 服务支持页看到的 |
| --- | --- |
| 认证用户 | D-12126615（服务中、1 条未读）+ D-12126572（服务中，远程已关），另一条已结束折叠 |
| 授权用户 | **无进行中的 case**，只有一条已结束的折叠入口，tab 无角标 |

实现上只需给 `epiqConversation` 与 `vereosConversation` 标 `audience: 'user'`。

## 7. 对话底部的三个终态

对话页底部只有三种可能，由**远程工单是否开着** × **报修状态**决定。

| # | 报修状态 | 远程工单 | 底部 | 样例 |
| --- | --- | --- | --- | --- |
| 1 | reported / in-service | 有 open segment | `MessageComposer`（占位符「回复工程师…」） | D-12126615 EPIQ Elite |
| 2 | reported / in-service | 全部 closed | 「在线沟通已结束，本次报修仍在处理中。」 | D-12126572 Vereos PET/CT |
| 3 | completed-pending | 全部 closed | 「报修服务已完成，沟通结束。」 | D-12126628 Azurion M3 |
| 3 | cancelled | 全部 closed | 「本次报修已取消，如仍需服务请重新报修。」 | 无 mock |

实现：`src/components/conversation-closed-note.tsx`，分支由 `isRepairStatusClosed(record.status)` 决定
（`['completed-pending', 'cancelled']`，定义在 `conversation-status.ts`）。

三个边界：

- **只有文字，不做按钮。** 先前的「致电××」「再次报修」按钮已删——这里只需要告知，不需要制造新的行动入口；
  报修入口在报修 tab，工程师电话在报修详情的服务工程师模块，都不应该在对话底部重复一遍。
- **同事的只读对话不渲染这个块**——不是你的报修，不该叫你去重新报修。
- **不提“致电”。** 报修仍在服务中时，场地工程师可能还没安排，根本没号可打；
  “怎么联系”完全交给报修详情的服务工程师模块。
- **报修已完成时不提“重新报修”。** 服务正常收尾，用户没有未竟事项，
  一句「报修服务已完成，沟通结束。」把两件事（服务结束、对话结束）说完即可；
  暗示“还得再报一次”反而像在提示出了问题。只有 **cancelled** 才保留「如仍需服务请重新报修」——
  取消意味着诉求没被满足，用户确实可能还要再来一次。

线程末尾的 `SegmentDivider`「本次在线沟通已结束」保留，它标的是**时间线上的那一刻**；
底部 note 说的是**接下来怎么办**，两者职责不同。

## 8. 对话页展示什么

页面只有四层：**导航 → case 卡 → 对话 → 输入框/结束提示**。

中间版本曾同时存在三层上下文：`caseBar`（设备名+报修号+两个链接）、`ThreadPartnerBar`（头像+当前对接）、
线程顶部的 `DeviceSummaryCard`。三者重复讲同一件事，而且那张卡因为开页自动滚到底部根本看不到。
现在只留 `ConversationCaseHeader`：

```
[图标] Vereos PET/CT                        ›   → 设备详情
       报修 D-12126572 · 服务工程师 陈工  [服务中] ›   → 报修详情
```

- **一张卡两行两个入口**，固定在顶部不随线程滚动，两行之间不加分隔线。
- 第 1 行是**设备**（图标 + 设备名），第 2 行左缩进 48px 与设备名对齐，是**这次报修**。
- 状态 chip 用 `record.statusTitle`，报修已结束时转灰；它是**报修**状态，
  必须留在第 2 行，放到设备行会被读成设备状态。
- 用户在和工程师聊的时候需要随手查设备（序列号、科室位置、保养、合同），
  **设备详情入口属于这里**，不属于报修详情页——那边加一块设备卡是大改页面结构。
- **不再放 `ThreadPartnerBar`**（组件保留在 `src/components/`，无人 import，作恢复路径）。

### 如何区分已结束与进行中

早期版本只靠头像颜色（32px 小圆）+ 一条极淡的细线，而**新一段的开头**却是 48px 蓝色大头像——
结束标记是耳语，开始标记是喊话，信号强度正好反了。现在三件事一起做：

1. **日期分隔**（`DateDivider`）——最有效。`ConversationThread` 把所有分段的消息拉平后标出每天首条，
   所以日期是**跨分段**的，不会因为换了工单而重复。
2. **已结束分段整体降档**（`opacity: 0.6`）——“旧”是**整段的属性**，不只是边界上的一个记号，
   滚到哪儿都能看出来。实现上把 `muted` 加在 `receivedBubble`/`sentRow`/`HandoffDivider` 上，
   **不要包一层 div**（会把 flex item 换成包装层，破坏 `alignSelf` 与 gap）。
3. **结束标记做重、接入标记做轻**：`SegmentDivider tone="end"` 改成实心 chip；Handoff 头像 48 → 32。

## 9. 工程师角色模型（重要）

飞利浦内部分两种，**对用户统一叫「服务工程师」**。界面上不出现“远程”“现场”这两个词。

| | 远程服务工程师 | 场地服务工程师 |
| --- | --- | --- |
| 何时出现 | **每个报修都有**，受理后先派 | 远程解决不了才安排 |
| 工单 | 远程维修工单（**必有**） | 现场维修工单 |
| 在线对话 | **有**，所有服务对话都是和他 | **无**，不在线沟通 |
| 电话 | 无 | **有** —— 电话图标就是场地工程师的标志 |

由此得出两条规则：

- **用渠道（在线 / 电话）替代角色（远程 / 现场）来解释为什么不能继续聊。**
  所以是「本次在线沟通已结束」而不是「本次远程服务已结束」。
- **`HandoffDivider` 写「服务工程师 X 加入对话」，不写「再次接入」。**
  “加入对话”对换人成立，也对将来的群聊（上下文同时共享给两类工程师）直接可用。
  同一人二次出现靠**日期分隔**区分，divider 本身不需要描述“第几次”。

## 10. 报修详情的服务工程师与服务记录

`src/pages/repair-detail-page.tsx`。

### 服务工程师

只展示**当前服务中的那一位**（一个报修背后可能有很多工单、很多工程师）。
渲染条件：`Boolean(record.progress.engineer) && !isPreCutoffRepair(record)`。
姓名与职称**同一行**（`周工  飞利浦服务工程师`）；职称固定为「飞利浦服务工程师」。
有电话按钮 = 当前是场地工程师；没有就不渲染按钮。

### 服务记录 = 工单 + 在线沟通

原「工单信息」改名为**「服务记录」**，内含两部分。两者同源——对话就是远程工单期间的沟通，
而且都是“这次服务做了什么”的记录；单拎一个「沟通记录」section 太重。

```
服务记录
────────────────────────────────
[远程维修] W0128924017
工单状态    进行中

[远程维修] W0128923901
工单状态    已完成

[在线沟通] 周工           ① 05/22  ›
```

在线沟通行与工单行用**同一套视觉语言**：同样的 `typePill` + 主体标识（工单是单号，沟通是工程师名）。

- **不放头像**——头像与周围的单据列表脉络脱节，显得突兀。
- **已冻结不做置灰**——这里本来就是“记录”，置灰反而奇怪；能不能回复点进去就知道。
- 右侧只有**未读角标 + 时间**，无副文本、无计数。时间格式见 `formatConversationTime`：
  当日 `H:MM` / 今年内隔日 `MM/DD` / 隔年 `YYYY/MM/DD`。
  “共 N 条”会让人分不清是 N 个工单还是 N 轮对话，而**工单粒度本就不该向用户暴露**。
- 只有 1 条可见对话时直接进 `ConversationPage`，>1 条才进 `CaseConversationsPage`。

### 工程师名字取哪个

**对话里的工程师 ≠ 报修单当前工程师。** 对话方永远是那位远程工程师，
`progress.engineer` 是当前服务中的那位（可能已换成场地）。
一律用 `conversationPartnerName(conversation)`，**绝不要回退到 `record.progress.engineer.name`**
——D-12126572 会显示成“与王工的对话”但点进去是陈工在说话。

4/18 前都是电话 / 服务号报修，数据侧本来就没有完整的工程师与进度，服务工程师模块不渲染，
服务记录只列工单（`isStatic`，不显示状态）。

## 13. 明确否决的替代方案

- **feature flag**：半接线的代码比"删掉 + 归档文档"更难维护。
- **去掉第 5 个 tab**：FAQ 与工程师对话记录仍需容身之处。
- **72 小时跟进窗口**：后台无法投递，等于换一种方式失约。
- **「工程师需要您补充信息时会在这里联系您」**：承诺了产品无法保证的事。
- **用热线替换所有被删入口**：热线不鼓励拨打，且多数入口本就不是死路。
- **入口行展示最后一条消息预览**：太重；且最后一句经常是用户自己说的（如 D-12126628
  结尾的「已签字，设备运行正常，辛苦了。」），预览出来没有信息量。改用「同名 + 同图标 + 同角标」建立关联。
- **服务结束后隐藏电话按钮**：工程师手机号不会因工单关闭而失效，
  与「没人盯的异步信箱」不是一回事。对外统一叫「飞利浦服务工程师」，所有工程师都给电话。
  （指的是**报修详情**里的电话按钮；对话底部的结束提示里不放任何按钮。）
- **在设备详情「总览」strip 里给对话单独开一条**：那条 strip 是设备状态告警列表，
  功能入口混进去会被读成状态。已并入「报修中」。
- **在报修详情顶部加一块设备卡**：设备详情入口属于对话页，不属于这里；
  报修详情已有「报修描述 → 报修设备」，再加一块是重复且大改页面结构。
